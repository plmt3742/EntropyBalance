# 关于"位置"而非"个人"的分析对象应如何建模

- 编号：B-02（对应 R-16）
- 优先级：P0
- 预计：4 人日
- 建议角色：产品/分析
- 决策用途：决定图谱的主节点是"人"还是"位置"；决定人员更替时是重建图还是只换占据者。这是产品与竞品拉开差距的概念基础。
- 前置：无；结论会影响 B-09、B-10 的建模。

## 1. 要回答的问题

1. 小型组织里的人如何理解"这件事该谁管"？他们说的是岗位、角色、还是"一直是他弄"？
2. "位置"的粒度是什么：一个职责？一组任务簇？一个决策权？能否被命名且稳定存在？
3. 位置从哪来：正式分工、重复出现的任务簇、关键决定的责任、还是负责人指定？
4. 位置与人是什么关系：一对一、一对多、多对一、空位？一个人占多个位置时如何表示负载？
5. 位置的生命周期：何时产生、合并、拆分、消失？换人时哪些属性保留、哪些重算？
6. 如何从记录中推断位置，而不是让用户先填岗位说明书？（这与"工具不能要求先规范填写"的前提直接冲突，必须解决。）
7. 位置模型与 RACI、Belbin 角色、岗位说明书的区别是什么？为什么不用现成的？

## 2. 调研需求

### 2.1 必须查的资料

- 角色理论（role theory）、团队角色（Belbin）、RACI/DACI、职务分析（job analysis）的基本概念。
- "位置/席位"在组织设计、责任分配、继任计划中的用法。
- ONA 产品如何处理"人—角色"而非"人—人"（Viva、OrgMapper、Orgvue 的官方说明）。

### 2.2 必须做的动作

1. 访谈 2 个小型组织，做一次卡片分类：让负责人把"团队必须有人管的事"写成卡片，再合并成位置，记录命名与合并理由。
2. 用同一批记录，尝试两种推断路径：任务簇聚类 vs 关键决定归属；比较哪种更接近人工卡片结果。
3. 做一次"换人"纸面演练：把某位置的人替换，问负责人"哪些属性不变、哪些要重算"。
4. 检查空位、兼任、多人共管三种情况能否表达。

### 2.3 产出物

- `docs/30-research/findings/B-02-position-model.md`。
- 位置模型：实体、属性、关系、状态、生命周期。
- 命名规则与合并/拆分规则。
- 2 个团队的位置清单（脱敏）与卡片分类记录。
- 一页"为什么位置比人更稳"的论证（用于答辩）。

### 2.4 验收标准

- 两个团队的位置清单，第三人只看名称能理解大致职责。
- 换人后位置数量与名称基本不变（变化 ≤20%）。
- 每个位置能指向 ≥2 个任务或 ≥1 个关键决定与证据。
- 空位、兼任、多人共管都有明确表示法。

## 3. 交互需求

### 3.1 用户要完成的动作

- 查看位置列表与位置卡（职责、当前占据者、备份、关联任务/决定）。
- 合并、拆分、重命名位置；把任务拖到位置下。
- 标记"空位"或"多人共管"。
- 执行"换人"模拟，查看风险变化。

### 3.2 界面必须表达的信息

- 位置是主节点，人是"当前占据者"，视觉上从属而非等同。
- 每个位置显示：任务数、关键任务数、备份状态、最近活动时间。
- 位置与人的多对多关系必须一眼看懂（一个人挂多个位置时，负载要合并计算）。
- 位置来源：自动推断 / 人工确认 / 手动创建，三者可区分。

### 3.3 必须支持的交互

- 合并/拆分可撤销；合并时显示将影响的职位、任务与证据。
- 拖拽任务改归属，立即重算负载与单点。
- 换人模拟不修改真实数据，退出即还原。
- 空位有明确视觉与文案，不显示为"某人"。

### 3.4 交互验收点

- 用户能在 2 分钟内完成一次"换人"并看到风险变化。
- 用户能说清"这个位置为什么存在"（点开能看到任务与决定证据）。
- 一人多位置时，负载不会重复计算或漏算。

## 4. 边界与禁止

- 不做岗位说明书、不做职级/薪酬、不做绩效。
- 不要求用户先填组织结构；位置必须能从记录推断或从少量确认中生成。
- 不把位置数量作为"组织健康"指标（位置多不等于好）。
- 不与正式 HR 系统字段强绑定。

## 5. 交付格式

按 findings 模板；额外附位置模型图（文字版即可）与 2 个团队的位置清单。
