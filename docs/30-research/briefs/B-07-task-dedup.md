# 关于同一任务跨记录的去重、状态演化与事件合并

- 编号：B-07（对应 R-06）
- 优先级：P1
- 预计：5 人日
- 建议角色：数据/抽取
- 决策用途：决定任务量与负载是否可信；不去重会虚增负载，导致"人人过载"的假结论。
- 前置：B-04（任务字段）。

## 1. 要回答的问题

1. 同一件事在周一、周三、周五各提一次，判定为同一任务的依据是什么：动作、对象、责任人、时间、还是上下文？
2. 任务有哪些状态：提出、确认、进行、阻塞、完成、取消、复活？状态之间允许怎么跳？
3. 子任务与父任务如何区分？"先做 A 才能做 B"与"B 是 A 的一部分"有什么语言线索？
4. 相似但不相同的任务（"整理报名表" vs "整理签到表"）如何避免误合并？
5. 合并后证据链如何保留？用户如何看到"这是一件事的三次提及"？
6. 错误合并与错误拆分的代价哪个更大？阈值应该偏向哪边？
7. 跨时间窗合并时，已完成的任务是否还参与负载计算？

## 2. 调研需求

### 2.1 必须查的资料

- 任务状态机与 issue tracker 的生命周期（Jira/OpenProject/Linear 的官方文档）。
- 事件抽取中的共指与事件合并（event coreference）基本方法。
- 文本聚类/相似度的常用阈值与评估方式（只需够用）。

### 2.2 必须做的动作

1. 从 30 条记录中人工整理 50 组"同一任务"与 50 组"相似但不同"的对照。
2. 定义合并键与相似度特征：动作动词、对象名词、责任人、时间邻近、上下文共现。
3. 实现粗聚类 + 语义相似度合并；记录每次合并的依据。
4. 定义状态机与允许的转移；标注 20 个任务的状态序列，验证状态机可表达。
5. 评估：错误合并率、错误拆分率、去重前后任务量偏差、人工确认工作量。
6. 做一次"极端重复"测试：同一任务被提及 10 次且措辞各异，看是否能合成一条。

### 2.3 产出物

- `docs/30-research/findings/B-07-task-dedup.md`。
- 合并规则与阈值、状态机定义、证据链结构。
- 50+50 对照集与评估结果。
- 去重前后指标对比（任务量、负载、Top-5 风险变化）。

### 2.4 验收标准

- 人工抽检 50 组，错误合并 ≤10%，错误拆分 ≤10%。
- 去重后任务量与人工计数偏差 ≤20%。
- 每条合并任务能展开看到全部原始提及与证据。
- 状态机覆盖 ≥90% 的真实状态序列；不允许的状态跳转有提示。

## 3. 交互需求

### 3.1 用户要完成的动作

- 查看任务时间线：提出、更新、阻塞、完成。
- 处理合并建议：合并 / 不合并 / 拆分。
- 手动修改状态；标记"复活"。
- 查看合并后的证据链。

### 3.2 界面必须表达的信息

- 合并建议卡：两条记录并排，差异高亮，说明"为什么认为是同一件事"。
- 时间线：每次提及的时间、说话人、状态变化。
- 合并后任务的"来源数"与"最后更新"，避免用户以为是新任务。
- 拆分时显示将影响的证据与指标。

### 3.3 必须支持的交互

- 合并/拆分可撤销。
- 合并时可选择保留哪个标题、哪个截止时间。
- 状态修改有历史记录，不覆盖。
- 从任务跳到原始记录与证据。

### 3.4 交互验收点

- 用户能看懂"这是一件事的第三次提及"（时间线 + 来源数）。
- 用户能一次拆分错误合并，并看到指标恢复。
- 合并后不会丢失任何原始提及。

## 4. 边界与禁止

- 不把相似主题当同一任务；不静默合并。
- 不覆盖原始记录；合并只是建立关联。
- 不用"任务数量"作为个人产出指标。
- 不为了减少任务量而过度合并。

## 5. 交付格式

按 findings 模板；额外附 50+50 对照集、状态机图（文字版）、去重前后对比。
