### 0.1 验收口径：本轮为「单人执行」

任务单 §2.2-4 / §2.3-4 / §2.4 都假定有**多位负责人**参与评分（≥50% 可执行、独立评分、可算一致性）。本项目实际只有 1 人可承担评审（参与者 0002），因此：

1. **不写「达标」**：单人评分不能推出「≥50% 的负责人认为可执行」，这一条在验收表里记为「未验证（本轮单人执行）」。
2. **能做的照做**：1 人仍可对 10 条建议逐条给「会做 / 可能做 / 不会做 + 理由」，这份数据照常存档（`data/samples/B-11-scoring-*.md`），并与 C 的拒绝测试分开记，不混算。
3. **一致性不计算**：单人没有「两人标注分歧」这回事，硬报一个 κ 就是造假；若将来凑到 ≥3 人，按附录 E 协议重跑即可补上。
4. **答辩口径**：「机制与确定性已做完并可用脚本复算；效果与可执行性需多负责人评分，本轮只有 1 人，未做多人验证」——这句话可以直接用，不需要修饰。

## 1. 结论（≤5 行）

1. **建议必须是「图上一次可命名的编辑」并且绑定具体对象**（任务/人/位置/依赖边）；不能绑定对象的「加强沟通」「提升意识」不进入建议列表，只能进「观察/备忘」，否则就是聊天机器人式废话。
2. **预期效果只能在快照上重算，不能由模型写**；每张卡必须标「重算（确定性）」或「定性（未仿真）」，并同时给绝对值、变化率（比率用百分点）、排名变化；多建议必须顺序应用、每步重算，因为 HHI、归一化、最大值使 Δ 不可相加。
3. **代价分两栏**：涉及人数、新增同步次数、影响任务数由系统估算；工时/学习成本默认用户填，系统只给结构性代理（是否参与过、是否同位置），不给假精度。
4. **7 类编辑足以覆盖任务单列举的干预**；但「拆位置」必须带显式承接分配，「结对」不等于「备份」，「补文档」是建模假设而非事实；「减范围」「转移决策权」「合并位置」暂不建模（列未决）。
5. **没有 B-09/B-10 也能交付机制与确定性**；不能交付的是效果含义、阈值、3 位负责人评分与真实因果。C 的 1 人 L3 试点只证明拒绝流程可走通，不等于建议有效；任何把合成夹具数字当团队结论的用法都违反本文件边界。

## 3. 对设计的影响

### 3.1 编辑类型学：7 类可建模，3 类不可/暂不建模

完整表见 **附录 A**。正文只给结论：

| ID | 编辑 | 一句话语义 | 可否仿真 | 关键限制 |
|---|---|---|---|---|
| E1 | `reassign` | 把任务责任人从 A 换成 B | 是 | 不能改已完成任务；B 若原是备份会被清空 |
| E2 | `add_backup` | 给任务指定一个备份 | 是 | 已有备份时不能静默替换 |
| E3 | `pair` | 增加共同承担者（contributor） | 是（只影响协作图） | **结对不等于备份**，不降低单点任务数 |
| E4 | `split_position` | 把一个位置拆给多个承接人 | 是，但必须显式分配 | 不给分配就拒绝，避免系统自造分配策略 |
| E5 | `document` | 标记任务已有可交接文档 | 是，但属建模假设 | 「有文档 = 可接手」不是事实，必须在卡片标注 |
| E6 | `defer` | 改截止日期（延期/降载的一种） | 是 | 只改日期，不改交付范围；不能改到过去 |
| E7 | `drop` | 取消任务 | 是，但只给警告 | 有下游时警告；不自动替用户决定是否可取消 |

**不建模 / 只能定性：**

- **减范围（reduce scope）**：当前图没有 scope 字段，无法计算「少做 20% 功能」的效果，只能定性；若要建模，需新增 `scope_items` 或 `acceptance_items` 字段（列未决）。
- **转移决策权**：Cross 的干预类型之一；当前 G_work 有 approver 角色但没有对应指标，重算不敏感，暂不生成。
- **合并位置**：与拆位置相反的组织操作；当前没有「位置合并」的编辑，列未决。
- **裁员/降薪/惩罚**：§4 明令禁止，不作为编辑类型。

### 3.2 数据模型与字段建议

不修改现有数据库；以下是 M7 实现时的**建议字段**（在 E09 的 `suggestion` 上扩展）：

| 字段 | 类型 | 必填 | 来源 | 说明 |
|---|---|---|---|---|
| `mode` | enum `recomputed` / `qualitative` | 是 | 系统 | 决定卡片是否允许出现数字 |
| `edit_ops` | array | 是（recomputed） | 系统/用户 | 每项含 `type` 与对象 id；qualitative 为空 |
| `primary_metric` | string | 是 | 规则 | 如 `spof_task_count`、`relative_load:P04` |
| `guardrails` | string[] | 是 | 规则 | 可能被牺牲的指标，如接收人负载、HHI |
| `expected_effect` | object | 是 | 重算 | `{primary[], guardrails[], computed, additivity}` |
| `cost` | object | 是 | 混合 | 可数项系统估算；`hours` 默认 null + `hours_source=user_input_required` |
| `affected` | object | 是 | 重算 | `{tasks[], people[], positions[]}` |
| `evidence` | array | 是 | 断言/图事实 | 每条含 `type/ref/note`，不能是散文 |
| `uncertainty` | object | 是 | 系统 | `{quantified:false, level, reasons[]}` |
| `rejection` | object/null | 否 | 用户 | `{code, note, would_accept_if}` |
| `applied_snapshot_id` | string/null | 否 | 系统 | 仅「接受并应用」后写入 |
| `order_index` | int | 否 | 系统 | 组合中的顺序，顺序敏感时必须显示 |

**原则**：`expected_effect` 里的数字只能由 `recompute()` 写；模型/前端不能写。`cost.hours` 没有用户输入时必须是 `null`，不能填一个「看起来合理」的数字。

### 3.3 指标与重算算法（provisional，待 B-09 定稿）

公式与 `analysis-model.md` v0.1 一致；本原型额外明确了三个口径：

```text
w(t) = u(t) × (1 + d(t))
u(t) = 3  若距截止 < 7 天
       2  若距截止 < 30 天
       1  其他（含无截止）
d(t) = 当前未完成的后继任务数（传递闭包）
T_crit = { 未完成任务 t | t 绑定对外截止，或 d(t) ≥ 2 }
effective_backup(t) = (backup(t) ≠ ∅) 或 documented(t)
SPI(v) = Σ_{t∈T_crit, owner=v, 无 effective_backup} w(t) / Σ_{t∈T_crit} w(t)
L(p) = Σ_{t 未完成, owner=p} w(t)
HHI_norm = (HHI − 1/n) / (1 − 1/n)
相对负载(p) = L(p) / median(L)
```

**必须写进卡片的三个口径说明：**

1. **`documented` 被当作可接手证据**：这解决 E08 中 §2.2 与 §4 的冲突，但它是假设。卡片必须写「文档化被视为可接手，未核验文档质量」。
2. **相对负载的分母是当前快照的中位数**：编辑本身会移动中位数。合成夹具里 P04 的 T11 改派后，相对负载从 2.2 变成 1.285714，并不是因为负载降了 42%，而是因为中位数从 5 变成 7。**卡片必须同时显示绝对负载和相对负载，并注明分母会随快照变化**；B-09 应决定是固定基线还是每次重算。
3. **备份不计入负载**：`L(p)` 只算 owner。一个人可以同时是 3 个任务的备份而负载不变。这是当前模型的盲区，代价字段必须单独给「新增备份责任数」，不能只说「新增同步 1 次」。

**确定性与数值规则：**

- 所有浮点四舍五入到 6 位；规范化 JSON（键排序、集合型数组排序）+ SHA-256，作为「同一建议重复计算一致」的证据。
- 变化率：`delta_pct = (after−before)/before×100`，**仅当 before≠0**；before=0 时返回 `null` 并显示「新增」，不能写「+∞%」。
- 比率型指标（SPI、HHI_norm、相对负载、协作密度）的差值用**百分点**（`delta_pp = delta×100`），不叫「%」。
- 排名：dense rank，1=最高；`rank_change = rank_before − rank_after`，正数=排名上升。
- 基线缺失（`null`）时不做比较，不补 0。

**组合与冲突：**

- 多建议按给定顺序逐条应用，每条都重算；输出每一步的 Δ 和累计 Δ。
- **Δ 不可相加**：E15 已给出反例（-0.008822 + -0.005514 ≠ -0.009925）。
- 硬冲突：前置条件不成立（任务/人不存在、owner 不匹配、任务已完成、已有备份、重复建议）。
- 软冲突/警告：`drop` 有下游、改派把关键任务的单点转移给接收人、接收人变过载、拆位置有人没分到任务。
- **顺序敏感**：对 ≤5 条建议尝试全部顺序（≤120 种），若最终快照哈希不同，标「顺序敏感」，要求用户确认顺序；>5 条不做全排列，标「未检查」。
- E16 的反例：拆位置与改派同一任务，两种顺序得到不同最终状态。

### 3.4 建议卡 7 字段与标注规则

完整模板与示例见 **附录 B**。字段固定为：

1. **问题**：`issue_id` + 一句话 + 具体对象；必须能指向任务/人/位置。
2. **编辑**：`edit_ops` + 人话摘要；定性建议此栏为「无图编辑」。
3. **预期效果**：`primary` + `guardrails`；每项含 before/after/delta/单位/百分比或百分点/排名变化；`source=recomputed`。
4. **代价**：涉及人数、新增同步次数、预计工时（null + 来源）、学习成本代理、影响任务数。
5. **影响范围**：任务、人、位置三列；来自前后快照 diff。
6. **证据**：断言/图事实的引用，不是散文；每条可跳转。
7. **不确定性**：`quantified:false` + 原因列表；不能写「高/中/低」了事。

**标注规则（硬性）：**

- 有图编辑且重算成功 → `mode=recomputed`，效果区必须出现数字，且每个数字带 `source=recomputed`。
- 无图编辑或无法重算 → `mode=qualitative`，效果区**不允许**出现 before/after 数字；只能写「定性（未仿真）」。
- 代价：`new_syncs` 标「系统估算」；`hours` 标「用户输入」；`learning_risk` 标「结构性代理」。
- 不确定性：当前统一 `quantified:false`，原因至少写「未含抽取置信度」「未含人员意愿」「阈值未标定」三条中的两条。

### 3.5 交互与状态机（已实现为单文件原型，合成数据 + 微快照空态）

```text
问题列表 ──> 建议卡 ──> 预览（临时快照，不落库）
                 │            │
                 │            ├─ 改参数（重算，重新出卡）
                 │            ├─ 接受 ──> 生成新快照 + 审计记录
                 │            └─ 拒绝 ──> 原因码 + 备注（可写「什么条件下会接受」）
                 │
                 └─ 定性观察（单独 tab，无「应用」按钮，只能记入备忘）

应用后 ──> 新旧对比（指标 + 受影响任务/人/位置） ──> 撤销（回到应用前快照）
```

**预览规则：**

- 预览只高亮将变的节点/边：任务卡改 owner/backup/contributors；人员卡改负载；位置卡改 holders；依赖边改上下游。
- 预览不写库；只有「接受」才生成新快照。
- 组合预览显示：每条建议的逐步 Δ + 累计 Δ + 软/硬冲突；顺序敏感时强制显示顺序选择。
- 撤销：回到应用前快照哈希；必须验证「撤销后哈希 = 应用前哈希」。

**验收对应**：能看出谁受影响（影响范围）、能拒绝留原因（原因码）、一键撤销数据完全恢复（哈希校验）、不把定性误认计算结果（mode 徽标 + 无数字）。

**原型实现（2026-11-19）**：

- 生成器：`scripts/b11_proto.py`；产物：`docs/30-research/prototype/b11-suggestion-cards.html`（单文件、离线、约 2.2 MB，含 6 张卡与 63 个非空组合快照）。
- 微快照页：`python scripts/b11_proto.py --snapshot data/samples/B-11-snapshot-micro-20261119.json --out docs/30-research/prototype/b11-suggestion-cards-micro.html` → 0 卡/0 组合/5 拒绝刺激；页面显示「快照 · 来源见备注」、`_note` 与空态原因，不再把部分快照叫「真实快照」。
- 三个 tab：建议卡 / 拒绝测试（试点）/ 边界清单；沿用 B-06 的深色样式与日志字段（`op_id/action/by/ts`），存储键 `b11_proto_v1`，支持导出 JSONL、`#reset`。
- 建议卡：7 字段、任务图高亮（橙色将变、红色虚线将删）、变体下拉（换承接人后重算）、工时用户输入、接受/仅接受/拒绝（原因码 + ≥10 字备注 + `would_accept_if`）。
- 组合：勾选 ≥2 条后显示累计指标与冲突，预计算 63 个子集；组合只对默认变体。
- 撤销：按「一次应用」为批次恢复 `applied/appliedCustom`，并校验撤销后哈希是否等于基准；不是只退最后一条。
- 拒绝测试：严格使用附录 E.4 的 X1–X5；X5 为 `PROHIBITED`，接受按钮禁用；记录耗时、原因码、备注，页面标明「试点，不计采纳率」。页首给出「你在扮演谁 / 接受=愿意作为下一步行动 / 拒绝=不愿、做不到、代价过高或违反禁止规则 / 5 问判断清单」，避免测试者无前置语境。
- 原型只证明交互与数据契约；**合成页数字不是真实团队数据，微快照页的 0 候选也不是风险结论**。

### 3.6 候选生成规则：如何避免「正确的废话」

原型实现的是**确定性规则**，不是 LLM：

| 规则 | 触发 | 生成 | 不生成时 |
|---|---|---|---|
| R1 | 关键任务无有效备份 | `add_backup`：优先 contributor，其次同位置同事；都没有但有未文档化 → `document` | 抑制，原因 `NO_CANDIDATE` |
| R2 | 相对负载 >1.5 且关键任务 ≥2 | `reassign`：从最大任务开始，选「接手后不超过 1.5×中位数」的接收人；跳过「关键且无备份」的任务，避免转移单点 | 抑制，原因 `NO_RECEIVER_WITH_CAPACITY` |
| R3 | 任何编辑 | 必须绑定 `task_id`/`person`/`position` + 一个 `edit_ops` | 不生成；「无建议」是合法输出 |
| R4 | 模拟后 primary 未改善，或 guardrail 恶化到阈值外 | 不生成，或降级为「观察」 | 记录原因，供后续评估规则精度 |
| R5 | 候选不足 10 条 | 按实际条数输出，**不凑数** | 评分时按实际条数，报告注明 |

合成夹具结果：6 条候选（5 条加备份 + 1 条改派），1 条被抑制（P01 过载但无接收人）。**这正好说明「无建议」是有信息量的**：P01 的问题不是换人能解决的，需要拆位置/加人/减范围。

### 3.7 如何验证「有用」

| 方法 | 能回答 | 不能回答 | 成本 | 本阶段 |
|---|---|---|---|---|
| 3 位负责人评分（会做/可能做/不会做 + 理由） | 是否能理解、是否愿意执行 | 真实效果 | 低 | 未执行，协议见附录 E |
| 采纳率（接受/拒绝/忽略） | 是否被使用 | 是否有效 | 低（需埋点） | 设计已给 |
| 前后指标对比 | 指标是否变化 | 因果（无对照） | 中 | 依赖 B-10 |
| 小规模试验（A/B、阶梯楔形） | 有限因果 | 泛化到小团队 | 高 | 当前不建议 |
| 拒绝原因分析 | 为什么不用、规则哪里错 | 效果 | 低 | 设计已给 |

**建议主口径**：采纳率 + 拒绝原因为主，前后对比为辅；**不声称因果**。B-11 §2.4 的「≥50% 可执行」建议定义为「会做 / 总数」，同时单列「会做 + 可能做」为「可接受率」；这个定义需要责任人确认（列未决）。

### 3.8 答辩口径

见 **附录 D**。三条硬规则：

- 说「在快照上模拟/预期」，不说「将会提升」。
- 不说「预测离职/失败」，不说「最优解」，不说「AI 自动优化」。
- 每张卡必须同时出现代价和影响范围，否则不许展示效果数字。

### 3.9 「什么建议不该给」边界清单（9 类）

这张表是原型「边界清单」tab 的数据源（`scripts/b11_proto.py` 的 `BOUNDARY`），也是候选生成与拒绝原因码的共同词表。**拒绝不是失败，是产品能力**：能说清「为什么不给」比多给一条更像聊天机器人的建议更重要。

| 代码 | 名称 | 判定规则 | 原型/系统行为 |
|---|---|---|---|
| `NO_OBJECT` | 没有具体对象 | 不能绑定 `task_id` / `person` / `position` 中至少一个；如「加强沟通」「提升意识」 | 不生成；外部输入直接拒绝并记录 |
| `INFEASIBLE` | 现实做不到 | 需要不存在的人/技能、已排满时间，或违反对外截止、法务、安全等硬约束 | 展示硬约束；拒绝记 `INFEASIBLE` |
| `TOO_COSTLY` | 代价高于收益 | 做得到，但新增同步/工时/学习/协调成本明显超过预期收益 | 卡片必须展示代价；拒绝记 `TOO_COSTLY` |
| `WRONG_DIAGNOSIS` | 诊断错误 | 依据的图事实/断言与数据矛盾，或把症状当原因 | 指向证据；拒绝记 `WRONG_DIAGNOSIS` |
| `BAD_TIMING` | 时机不对 | 现在做会与对外截止/关键窗口冲突，但未来可做 | 记录何时可做；拒绝记 `BAD_TIMING` |
| `ALREADY_RESOLVED` | 已经解决 | 问题已被别的编辑解决，或快照已过期 | 先查当前快照；拒绝记 `ALREADY_RESOLVED` |
| `PROHIBITED` | 违反禁止规则 | 裁员、降薪、惩罚、公开排名羞辱，或越过负责人做人事决定 | 不生成；外部输入硬阻断 |
| `PROMISE` | 承诺效果/因果 | 「保证提前两周」「一定提升效率」等 | 不生成；改为「模拟/预期」并标不确定性 |
| `CONFLICT` | 与已有建议冲突/重复 | 同一任务被两条建议改 owner，或一条依赖另一条先执行 | 组合面板显示软/硬冲突；硬冲突不允许一键全应用 |

### 6.3.1 单人评分实测：结果不能用（对照失败）

材料 `E:\计算机设计大赛\_工作台\B-11-建议评分-单人-20261119.html`，10 条 = 6 条重算建议（合成夹具算出：5 条「关键任务无备份」+ 1 条「负载超阈值」）+ 4 条**故意写的空话**（"加强沟通""提升责任意识""每周复盘会""引入 OKR"）。评审人 0002，原始导出 `b11-scoring-0002.jsonl`（10 行）。

| 项 | 结果 |
|---|---|
| 会做 | 9 / 10 |
| 可能做 | 1 / 10 |
| 不会做 | 0 / 10 |
| 6 条重算建议 | 会做 5、可能做 1 |
| **4 条空话** | **会做 4（本应全部落在「不会做」）** |

**结论：这批数据不能用。** 判定为「会做」的 9 条里，理由高度重复（"做好任务交接可以把任务进行下去"这类一句话被复用到 5 条），**没有一条指出该改哪个任务、找谁**——说明评审人回答的是"这个方向听起来对不对"，不是"我明天会不会动手"。而这正好是任务单要防的失败模式（§2.4「而非听起来对」），所以不能把这 90% 当成通过。

**原因（我方设计问题，不是评审人的问题）**：
1. 单问「你会不会做」对空话天然友好——"加强沟通"人人都会说会做，因为它不需要任何具体动作。
2. 页面把 6 条与 4 条混排、同一套三档按钮，没有先问"这条有没有指出要改哪个任务"，等于把区分工作丢给了评审人。
3. 脱敏后无法判断"某人能不能胜任"，进一步把判断推向"方向对不对"。

**决定：不重测（责任人 0002，2026-11-19）。** 两问版页面已生成（`B-11-建议评分-二问-20261119.html`）但**未执行**，作为“下次若重做该怎么做”的备选留档；本轮以第一版数据为最终记录，验收表第 3 条维持「未通过（对照失败）」。

**修法（备选，未执行）**：改成两问——
- 问 1（客观，可核对）：这条有没有指出**具体要改哪个任务、或指定谁**？（有 / 没有）→ 对 4 条空话，正确答案是"没有"，这一问就有判别力。
- 问 2（主观）：若问 1 为"有"，你会做吗？
只有问 1 通过的建议才计入可执行率；空话一律先被问 1 筛掉，不再进入主观判断。

****本文任何地方都不出现「可执行率 ≥50%」这类表述**，答辩口径为「做了 1 人评分，但对照检查发现判据没有判别力，因此不作为可执行性证据」。**

## 附录 C 重算口径与实现说明

### C.1 文件

| 文件 | 作用 |
|---|---|
| `scripts/b11_recompute.py` | 纯标准库原型：校验、指标、编辑、组合、卡片、候选、CLI |
| `scripts/b11_recompute_test.py` | 32 个 `unittest` 用例 |
| `data/samples/B-11-fixture-synthetic.json` | 合成夹具（`_synthetic: true`，不代表真实团队） |

### C.2 算法（伪代码）

```text
compute_metrics(snapshot):
  succ = transitive_successors(deps)          # 有环则报错
  for task in tasks:
      w[task] = 0 if done else u(deadline) * (1 + active_successors)
      crit = external_deadline or active_successors >= 2
  SPI(p) = sum(w[t] for t in crit if owner==p and not effective_backup(t)) / sum(w[crit])
  load(p) = sum(w[t] for t in active if owner==p)
  HHI_norm = normalized(sum((load/total)^2))
  orphaned(p) = count(active tasks owner==p and not effective_backup)
  cascade(p) = count(active successors of orphaned(p))
  collab = undirected graph over co-participants of active tasks
  cut_points = tarjan(collab)

apply_suggestion(snapshot, suggestion):
  current = snapshot
  for op in suggestion.edit_ops:
      before = compute_metrics(current)
      current = apply_edit(current, op)       # 深拷贝，失败不改 current
      after = compute_metrics(current)
      steps.append(diff(before, after))
  return {steps, cumulative: diff(metrics(snapshot), metrics(current)), hash_after}
```

### C.3 数值与格式化

- 所有浮点 `round(x, 6)`；`-0.0` 归一为 `0.0`。
- 快照哈希：`normalize_snapshot()`（人员/任务/依赖排序、contributors 排序）→ `json.dumps(sort_keys=True, separators=(",",":"), allow_nan=False)` → SHA-256。
- `delta_pct`：before=0 → `null`；UI 显示「新增」。
- 比率指标：`delta_pp = delta × 100`，单位写「百分点」。
- 排名：dense；`rank_change = before - after`，正数=上升。

### C.4 组合规则

1. 按用户给定顺序逐条应用；每条内部 `edit_ops` 顺序固定（语义上是一张卡）。
2. 每条后立即重算；输出逐步 Δ 与累计 Δ。
3. 硬冲突：前置条件失败、重复建议 id、同一对象冲突编辑。
4. 软冲突：`drop` 有下游、改派转移单点、接收人过载、拆位置有人无任务。
5. 顺序敏感：≤5 条全排列；>1 个最终哈希 → 标「顺序敏感」；>5 条标「未检查」。
6. **不把单条 Δ 相加当组合 Δ**；E15 是反例。

### C.5 代价规则

| 编辑 | 人数（S） | 新增同步（S） | 工时（U） | 学习代理（S） |
|---|---|---|---|---|
| reassign | 2 | 1 | null | 有参与/同位置→low，否则 unknown_high |
| add_backup | 2 | 1 | null | 同上 |
| pair | 2 | 2 | null | 同上 |
| split_position | k | k | null | 按承接人是否接触过任务 |
| document | 1 | 0 | null | — |
| defer | 1+下游 | 下游数 | 0 | — |
| drop | 1+下游 | 1+下游 | null | — |

`effort_weight_units` = 受影响任务的权重和，仅作相对量，**不是工时**。

### C.6 已知限制

- 备份不计负载（见 §3.3）。
- 相对负载分母随快照变化（见 §3.3）。
- `documented` 是假设（见 C1）。
- 协作图只取未完成任务；已完成任务的历史协作不计。
- 割点只在密度 ≤0.7 时可信；密度 >0.7 需 B-09 的二部流图支配点（未实现）。
- 顺序敏感只检查 ≤5 条。
- 没有 UI、没有数据库、没有真实数据。

## 附录 D 一页答辩稿：与通用聊天机器人的区别

> 用途：答辩/评审时单页讲述；可单独打印。**所有数字示例均为合成夹具，不冒充真实团队结果。**

### D.1 一句话

我们做的不是「让 AI 给团队提建议」，而是**把建议变成图上一次可命名的编辑，再在快照上重算它的后果**；AI 可以帮忙发现问题，但不能替我们写结论。

### D.2 五条区别

| 维度 | 通用聊天机器人 | 本系统 |
|---|---|---|
| 问题从哪来 | 用户随口问，模型自由联想 | 从 G_work/G_dep/G_collab 的断言来，带 `issue_id` |
| 建议是什么 | 一段自然语言 | 一条 `edit_ops`：改哪个任务/人/位置/依赖边 |
| 效果怎么来 | 模型「估计」 | 代码在快照上重算，输出 before/after/Δ/排名 |
| 代价与影响 | 通常没有，或一句「需要投入」 | 人数/同步次数/工时（用户填）/任务/人/位置 |
| 边界 | 什么都敢答 | 不能绑定对象的建议不展示；不自动执行；不承诺效果 |

### D.3 一张图

```text
断言（谁/什么/为什么） → 问题（issue_id）
        │
        ▼
编辑（reassign / add_backup / pair / split_position / document / defer / drop）
        │
        ▼
重算（同一快照 → 新快照；SPI / HHI / 负载 / 单点 / 断档）
        │
        ▼
卡片（问题 / 编辑 / 预期效果 / 代价 / 影响范围 / 证据 / 不确定性）
        │
        ▼
人决定（接受 / 拒绝+原因 / 改参数 / 撤销）
```

### D.4 一个具体例子（合成数据）

T01 是对外演示环境，P01 负责、没有备份，且 T01 阻塞 3 个后续任务。系统给的建议是「为 T01 增加备份 P04」，不是「加强知识共享」。重算结果：单点任务数 5→4（-1，-20%）；最大负载、HHI、协作密度不变；代价是 2 人、1 次交接同步、工时待负责人填；影响范围是 T01 与 P01/P04。负责人可以接受、拒绝（选原因）、或改成 P05 再算一次。

### D.5 评委可能问的三个问题

**问：这不就是 ChatGPT 加模板吗？**
答：模板只是外壳。区别在「数字从哪来」：我们的每个数字都能追到一次图编辑和一次重算；模型不参与写数字。没有图编辑的「建议」在我们这里不允许展示为建议。

**问：效果可信吗？**
答：我们不说「可信」，我们说「可复现」：同一建议在同一快照上重复计算完全一致；换快照就重算；不确定性明确标「未量化」，因为还没接 B-09 的置信度。真实效果要靠负责人评分、采纳率和前后对比，不靠模型声称。

**问：为什么不自动执行？**
答：因为建议改变的是人的工作安排，不是改一个配置。我们坚持人在环：预览不落库、接受才生成新快照、拒绝要留原因、应用后可撤销。自动执行会把「模拟」变成「既成事实」，这是我们明确禁止的。

### D.6 不要说的话

- 「AI 能预测谁要离职」——不，模型不做这个。
- 「建议能提升 30% 效率」——不，只有快照上的模拟值，且未验证。
- 「这是最优解」——不，只是候选之一。
- 「全自动优化团队」——不，人在环是硬约束。
