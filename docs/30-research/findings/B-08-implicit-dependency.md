# B-08 关于隐式依赖与隐性承诺的识别边界

- 调研人：mtb · 0003
- 完成日期：2026-11-18
- 对应单子：`briefs/B-08-implicit-dependency.md`
- 状态：部分完成。词典、句式、提示词与展示规范已完成；评估的分母小于任务单要求，原因见第 5 节。

> 本文回答一个问题：中文会议记录里，什么样的句子可以连成一条依赖边，什么样的句子不行。
>
> 三条行文约定：
> 1. 结论只写「能判定什么、判不了什么」，不写「识别率很高」这类没有分母的话。
> 2. 每条规则都配反例。只给正例的词典，用起来一定过抽。
> 3. 承认漏判。依赖识别的默认策略是宁可漏、不可错，原因在第 1 节第 4 条。

## 1. 结论（≤5 行）

1. 中文的依赖线索集中在两类结构：条件句（「等 X 弄完才能 Y」「没 X 就没法 Y」）和动作先后（「先 X 再 Y」「X 之后 Y」）。单看词表不够，必须看句子里有没有两个动作。
2. **承诺不等于依赖。** 承诺是人对事（「我来吧」），依赖是事对事（「我这边等着切图」）。把两者混为一谈，会把「谁答应了」错算成「谁卡着谁」。
3. 强弱的界线不是语气，而是后果：缺了它任务交不了，是硬依赖；缺了它还能交、只是变差，是弱依赖。
4. 精确率优先是对的。多抽一条假边，阻塞链就会指向一个没有责任的人；漏一条真边，只是少发现一个风险。前者会毁掉结论的可信度。
5. 盲评结果：硬依赖精确率 0.82、方向错误率 0.00，达到验收线；反例误抽率 0.16，超出 10% 上限；6 条弱依赖一条都没识别出来。提示词能处理显式条件句，处理不了「可以绕开的依赖」。

### 2.2 依赖类型与语言线索

类型划分参照协调理论（Malone & Crowston, 1994, *The Interdisciplinary Study of Coordination*, ACM Computing Surveys 26(1), DOI 10.1145/174666.174668）的四类依赖，以及设计结构矩阵（Eppinger & Browning, 2012, *Design Structure Matrix Methods and Applications*, MIT Press）对依赖强弱的表示，按中文语料的可操作性调整为五类：

| 类型 | 含义 | 典型词 | 典型句式 | 反例（看着像，其实不是） |
|---|---|---|---|---|
| 前置 | 一件事的产出是另一件事的输入 | 等、先、之后、再、才能、卡在、得等 | 「等 P04 定稿再动」「卡在登录接口上」「得等数据结果」 | 「先这样吧」「之后再聊」——没有第二个动作，只是收尾语 |
| 资源 | 两件事争用同一个不可并行的人、设备或时段 | 只有、没…跑不起来、借用、占用、还 | 「只有 P03 电脑能跑」「那台机器月底要还」 | 「我电脑上有」——描述状态，不是约束 |
| 审批 | 需要外部批准或走流程才能继续 | 审批、报备、批下来、走流程、同意、备案 | 「要走学院审批」「备案没下来之前」 | 「老师说要做」——这是需求转述，不是审批节点 |
| 信息 | 缺一条信息就动不了或做不对 | 确认、问一下、给我一份、口径、门牌号 | 「先给他一份接口文档」「门牌号是多少」 | 「问一下他最近怎么样」——社交问候，不承载任务 |
| 同步 | 需要在同一时间点对齐 | 对齐、对一下、同步、碰一下、一起 | 「等讲稿定了再对」「发群里方便后续同步」 | 「一起吃饭」——社交活动，不是任务对齐 |

**工具侧的对照。** 商业项目管理工具不自动判定依赖，而是让用户手选链接类型。核对两个有公开文档的工具：

| 工具 | 公开的链接类型 | 与我们五类的对应 |
|---|---|---|
| Jira | is blocked by / blocks / relates to / duplicates / clones | blocks 与 is blocked by 对应「前置」，默认按硬处理；relates to 太泛，不映射；duplicates、clones 不是依赖 |
| OpenProject | Related to / Predecessor-Successor（旧称 Precedes-Follows）/ Blocks-Blocked by / Requires-Required by / Includes-Part of / Duplicates | Predecessor/Successor 对应「同步」的时间约束；Blocks 对应「前置」；Requires 最接近「弱依赖」的容器；Includes 是层级，不是依赖 |

来源：Atlassian Support《Link work items》，访问 2026-11-18；OpenProject Docs《Work package relations and hierarchies》，访问 2026-11-18。

由此得出两点，直接影响设计：

1. 强弱在商业工具里是人工选择，不是判定结果。用户选 Blocks 就是硬，选 Requires 就是弱，工具不检查原文。我们的差异不在类型多少，而在于从原文自动判定并附证据。
2. 它们没有「证据」字段。每条链接只有一个描述框，可以随便填。所以它们能回答「谁依赖谁」，不能回答「凭什么这么判」。这也是本文坚持 ev 必填的原因。


### 2.3 承诺与客气的分界

承诺会出现，但不等于依赖。判断承诺只需要回答两个问题：谁做、什么时候或什么条件下做。

| 等级 | 说法 | 判据 | 例（来自语料） |
|---|---|---|---|
| 明确承诺 | 「我今晚填，明天上午发你」 | 有主体、有动作、有时间 | `R004` |
| 有承诺无时间 | 「我来吧」「我盯着」 | 有主体、有动作，缺时间 | `R009` |
| 弱承诺 | 「我看看」「回头弄」「这周吧」 | 动作模糊，时间模糊，结果不承诺 | `R007`、`R020`、`R022` |
| 不是承诺 | 「辛苦了」「麻烦了」「谢谢」 | 无动作，或动作指向情绪而非任务 | `R013`、`R029` |
| 不是承诺 | 「如果评委问，他来讲」 | 假设句；条件不成立时承诺不生效 | `R028` |
| 不是承诺 | 「老师说要交一版」 | 转述他人要求，说话人未承诺执行 | `R009` |

结论：弱承诺可以进入「待确认」队列，但不应当直接连成依赖边。它缺的是结果承诺，而依赖边要求的是确定的约束。

### 2.4 判定提示词 v1

完整提示词如下，要求稳定输出、可复算：

```text
你是组织协作分析中的「依赖判定器」。输入是一句来自会议纪要或工作群聊的中文原文。

判定标准：
- 依赖（dep=1）：一个任务要完成，必须以另一个任务、资源、批准或信息为前提。
  句中能看出「A 需要 B」的约束关系。
- 承诺（dep=0，type=承诺）：说话人表示自己将要做某事，含明确意愿或时间。
  承诺本身不构成对他人的依赖，单独归类。
- 两者都不是（dep=0，type=无）：寒暄与礼貌语、假设句中的假设部分、玩笑、
  转述他人原话但不是说话人自己的任务、单纯提到某人某物、纯进度陈述与意见。
- 硬（str=硬）：缺少被依赖项，任务无法完成。
- 弱（str=弱）：缺少被依赖项，任务仍可推进，只影响质量、效率或体验。
- 方向写作「依赖方<-被依赖方」，用任务名或角色名，不要编造句子里没有的编号。
- 证据 ev 必须是原文精确子串，不得改写、不得补充。
- 宁可漏，不可错：不确定时判 dep=0，并写明原因。

输出（每行一个对象）：
{"id":"S001","dep":0,"type":"前置|资源|审批|信息|同步|承诺|无",
 "dir":"","str":"硬|弱|无","ev":"","conf":0.0,"reason":"不超过 20 字"}

约束：dep=1 时 type 只能是五类之一，dir 与 ev 必填；
dep=0 时 str 填「无」（type=承诺 时可填硬/弱）。
```

提示词里刻意做了三处取舍：

1. **把承诺单列，而不是折进依赖。** 否则「我来吧」会被抽成一条指向自己的边，图上会出现自环。
2. **要求证据是原文子串。** 这样每条边都能回跳原文，也拦住了模型改写句子来凑证据。
3. **不确定时判 0。** 召回率会下降，但精确率可控；这与任务单「不为了召回牺牲精确率」一致。

### 2.5 评估结果

评估方式：把 100 条句子去掉标签，交给另一个未看过标注的模型按上述提示词独立判定，再与标注逐条对账。

方向一项由人工核对等价性。模型写的是「切图<-登录页设计稿」，标注写的是「P02 页面开发<-P04 登录页稿」，语义相同但字面不同；若按字符串比对，会把正确的方向判成不匹配。因此方向按语义判定，并记录这一处理。

| 指标 | 结果 | 计算口径 |
|---|---|---|
| 硬依赖精确率 | 0.818（18/22） | 预测为硬依赖，且类型、方向均正确 |
| 弱依赖精确率 | 0.000（0/6） | 模型判为弱的 6 条，标注里全是硬依赖 |
| 弱依赖召回 | 0.000（0/6） | 标注为弱的 6 条，一条也没被判成依赖 |
| 方向错误率 | 0.000（0/23） | 类型判对的依赖条中，没有一条判反 |
| 反例误抽率 | 0.161（5/31） | 31 条反例中 5 条被判成依赖或承诺 |
| 承诺精确率 | 0.773（17/22） | 预测为承诺的条数中，标注确为承诺 |
| 承诺召回 | 0.548（17/31） | 标注为承诺的条数中被识别出来 |
| 漏判 | 12/38（31.6%） | 标注为依赖但判成非依赖 |

混淆矩阵：

|  | 预测依赖 | 预测承诺 | 预测都不是 |
|---|---|---|---|
| 标注依赖（38） | 26 | 0 | 12 |
| 标注承诺（31） | 0 | 17 | 14 |
| 标注都不是（31） | 2 | 3 | 26 |

失败类型（按影响排序）：

1. **弱依赖整体失守。** 6 条全漏，其中 6 条被判成非依赖。提示词只问「缺了它任务能不能完成」，没有给出「能完成但会变差」的判据，模型自然把可绕开的都判成不依赖。这是 v1 最明确的缺陷。
2. **强弱混淆。** `S027`「切图要标注，不然还原度低」、`S041`「结果等图出来再填」标注为硬，模型都判成弱，理由都是「可以后补」。说明「后补」与「绕开」在提示词里没有区分。
3. **类型混淆。** `S051` 数据重做属于资源占用，被判成前置；`S060` 审批通过属于前置条件，被判成审批；`S077` 原文已明写「依赖」，仍被判成信息。三处都发生在相邻类型之间。
4. **建议与请求被误判成依赖。** `S022`「这周先不定，等下次评审再说」是决策悬置，`S062`「能重截吗」是请求，都被判成依赖。前者把「暂缓」读成了「等待」，后者把「请求」读成了「已成立的前提」。
5. **无主语的群体任务漏判。** `S093`「检查是否有电」、`S094`「把信息发群里」都没落边。这类句子没有主语，方向和责任人都缺，模型选择了保守。

值得记录的一点：**31 条承诺中，没有任何一条被判成依赖。** 说明「承诺不等于依赖」这条边界在提示词里立住了，没有出现自环或把人当依赖的情况。

## 3. 对设计的影响

### 3.1 数据模型

一条依赖边至少需要五个字段，缺一不可：

| 字段 | 取值 | 为什么必要 |
|---|---|---|
| `type` | 前置 / 资源 / 审批 / 信息 / 同步 | 决定修复建议：缺前置要排期，缺审批要催流程 |
| `strength` | 硬 / 弱 | 决定是否进入关键路径（见 3.3） |
| `evidence` | 原文片段 + 记录 ID | 支撑「每条结论都能展开到原文」 |
| `confidence` | 0–1 | 低置信度进入确认队列，而不是直接上图 |
| `direction` | 依赖方 <- 被依赖方 | 方向反了，阻塞链会指错人 |

建议：不存「依赖强度」的单一分数。强和弱是两种性质，不是一个连续量的两端。

### 3.2 置信度与入图门槛

- `confidence ≥ 0.8` 且证据完整：直接入图。
- `0.5 ≤ confidence < 0.8`：入图但标为待确认，图上用虚线，进入人工确认队列。
- `confidence < 0.5`：不入图，只在「疑似线索」列表里保留，供人工提升。

这与任务单「无证据的边不入图」一致：没有 ev 的边，无论置信度多高都不入图。

### 3.3 弱依赖的展示规范

| 维度 | 硬依赖 | 弱依赖 |
|---|---|---|
| 线型 | 实线 | 虚线 |
| 参与关键路径计算 | 是 | 否 |
| 参与单点判定 | 是 | 否 |
| 图上默认可见 | 是 | 可折叠，默认关闭 |
| 断档提示强度 | 阻塞（红） | 降级（黄） |
| 文案 | 「必须等」 | 「最好等」 |

补充规则：

- 弱依赖不参与支配点与关键路径的计算，只作为「如果时间允许」的优化提示。原因是弱依赖一旦进入关键路径，几乎每条边都会变成阻塞点，结论失去区分度。
- 强弱可以人工改判。改判后立即重算受影响的阻塞链，并在图上标出「人工修改」。
- 环检测对硬依赖生效；弱依赖成环只提示、不阻断。

### 3.4 图上的最小表达

用户需要在一眼之内回答三个问题：这条线是必须的还是可选的、方向朝谁、依据是什么。

- 方向：箭头由被依赖方指向依赖方，表示产出或放行的流向；与「依赖方<-被依赖方」的写法一致，读作「A 在等 B」。全项目只用这一种记法。
- 类型：用颜色区分五类，但颜色不是唯一编码，同时带文字标签，照顾色觉差异。
- 证据：点边即展开证据句、判定理由、置信度与来源记录。
- 环：出现硬依赖环时，提示「这组依赖形成环，可能是数据错误」，并高亮环上置信度最低的一条，建议先核对。

## 4. 下游指标影响的初步观察

用 38 条依赖（32 硬、6 弱）搭一张图，观察弱依赖与噪声对结论的影响。这只是定性观察，未做仿真：

1. **弱依赖进关键路径会稀释结论。** 若把 6 条弱依赖一并算入关键路径，被标为「单点」的节点从 2 个增加到 5 个，其中 3 个在现实中并不构成阻塞。
2. **方向错一条，责任就指错人。** 「联调<-登录接口」若判反，阻塞链会把 P02 标成阻塞源，而实际卡住的是 P03 的接口。
3. **无主语任务最难落边。** 真实片段里的「确认麦克风在谁那里」「检查是否有电」都没有主语，方向只能记在「活动组」上，这会让该节点的责任看起来比实际更分散。
4. **承诺未兑现会形成孤立点。** `R007` 的「回头弄」没有后续记录，图上看不出它其实一直没做；要发现这类问题，需要跨记录比对承诺与事实，而不是单句判定。

## 5. 分歧与未解决

1. **评估分母不足。** 任务单要求「100 条含依赖或承诺线索的句子」，本次 100 条标注中只有 69 条含线索（38 依赖 + 31 承诺），其余 31 条是反例。原因是 33 条记录的总句数有限。若要把正样本补到 100 条，需要把记录扩到 60 条以上。
2. **合成语料偏规整。** 合成记录的句式比真实群聊整齐，指标偏乐观。真实片段只有 3 条，且都是短时对话，不足以校正。
3. **玩笑类反例缺失。** 语料里没有玩笑，因此「玩笑误抽」这一类没有测到。
4. **建议语气的归类未定。** 「建议从这些批次中选取」被判为弱依赖，但也可以看作决策依据而非依赖。需要产品侧定口径。
5. **无主语任务的归属未定。** 「确认麦克风在谁那里」应落到谁头上：发起人、@到的群体、还是默认的活动负责人？三种记法会让图完全不同。
6. **承诺与依赖的关系未定。** 本文把承诺单列，不连边。但如果产品希望「谁答应了什么」也能进入图，需要新增一种边类型，而不是复用依赖边。
7. **弱依赖召回为零。** v1 提示词没有给出弱依赖的判据，6 条全部漏判。在补上判据之前，弱依赖不应进入对外演示。
8. **未查阅中文情态语言学的专门文献。** 第 2.3 节的承诺分级来自语料观察，不是语言学框架。任务单要求的这部分只做到「够用」，没有做到「有出处」。

## 6. 下一步建议

1. 由队长确认第 5 节第 4、5、6 条三个口径，再定评估脚本的比对规则。
2. 补语料：把记录扩到 60 条以上，优先补真实群聊，特别是含玩笑、反讽、跨天承诺未兑现的段落。
3. 提示词做 v2：补三条判据——弱依赖（能完成但变差）、建议与请求不属于依赖、一句多边要拆分。同时把这次误抽的 5 条（`S006`、`S022`、`S056`、`S062`、`S099`）作为回归用例固定下来。
4. 评估脚本化：把对账写成脚本，固化混淆矩阵与三项指标，后续改提示词可直接复算。
5. 弱依赖单独建一份小标注集（目标 30 条），否则弱依赖的精确率始终只有一个位数样本。
