## 3. 切片口径

| 约定 | 内容 |
|---|---|
| 切法 | **时间窗**：按消息出现顺序切，一段 15–30 条，不按议题重组 |
| 为什么 | 保留连续原文，`evidence.span_start/span_end` 才有意义；议题重组会切断证据链 |
| 跨记录同一议题 | 用 `merge_key`（标注阶段填）串联，不合并记录 |
| 记录长度 | 约 100–400 字/条（本批 12 条共 2935 字） |
| 编号 | `R-101` ~ `R-112`（与构造案例 `R-001`~`R-029` 不重叠） |
| 偏移单位 | Unicode 码位（`unicode_code_point`），由 `build` 脚本按 `quote` 自动计算 |

## 4. 已知缺陷

1. **没有时间戳**。粘贴出来的文本丢失了每条消息的时间。`record.captured_at` 统一填 `2026-11-17T21:00:00+08:00`，属**估算值**。依据：聊天里说「本周日」与「老师让我们建议22号」，而 2026-11-22 是周日，故判断此段发生在 11-22 之前的一周内。
2. **没有日期**。连"哪一天"都只能靠上述推算；跨记录的先后顺序可信，绝对时间不可信。
3. **图片、视频、合并转发的聊天记录缺失**。原文中的 `[图片]`、`[视频]`、`[聊天记录]` 保留了占位符，内容不可得。
4. **发言人可能缺失**。合并转发有时会丢失发言人，本批未发现，但不能保证。
5. **可能有错字**。原文经人工转录，未逐字校对。
6. **合规缺口**：原始文本未经本地脱敏即粘贴给处理人，意味着它已经过一次模型服务。若后续要用于论文或对外材料，需要队长与群成员书面同意，或改用 `scripts/redact-chat.py` 在本地先脱敏再提供。

## 5. 每条记录的定位方式

`evidence.quote` 是原文逐字片段，可直接在本文件的 `B-04-real-records.jsonl` 里搜索定位；
`span_start/span_end` 是 `quote` 在 `text` 字段中的码位区间，由脚本计算，可机器复核。
